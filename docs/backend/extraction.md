# Extraction: image to reviewable scorecard

The active scanner is implemented across Services and the scan router. The legacy `llm/` directory contains no Python source in this checkout, so older FULL/SCORES_ONLY/SMART documentation should not guide new edits.

## Current flow

1. Frontend scan hooks prepare an image/PDF and player/course hints. OCR can be prefetched before extraction.
1. [scan_uploads.py](../../api/scan_uploads.py) checks the upload (name, content type, 20 MB, decodable image within the size caps, or a parseable PDF) and owns its temporary files: only the request creates temporary files and removes every one afterwards (including after a cancelled request or a failed write, flush or close), logging rather than raising a cleanup failure. File and image work runs in a worker thread that only writes into those existing files and never creates one, so a worker still running after its request was cancelled can't recreate a deleted file. [scan_image.py](../../services/scan_image.py) prepares the OCR input: a browser-ready 2,000 px JPEG passes through, other images become a 2,000 px quality-80 JPEG without metadata, and PDFs go to OCR as uploaded. `/extract` with prefetched OCR text validates the upload but doesn't re-encode it. `/ocr` has no user or database dependency.
2. [mistral_ocr_service.py](../../services/mistral_ocr_service.py) calls Mistral (HTML tables) and cleans each table up deterministically before anything else sees it: merged cells (`rowspan`/`colspan`) are expanded into the grid, and data rows that are wider or narrower than their hole header are aligned to it (a name in its own cell, a tee rating after the label, a missing `INITIALS` separator column). Only structure that the table itself proves is changed; anything else is left alone and reported.
3. [scan_ocr.py](../../services/scan_ocr.py) orchestrates OCR and merging. It rejects cleaned OCR text over `MAX_OCR_TEXT_CHARS` before the paid merge call and checks the merged result against the same limit. Both `/ocr` and `/extract` return 422 for oversized text; `/extract` identifies the failure as `unreadable_scores` at stage `ocr`. [gemini_table_merger.py](../../services/gemini_table_merger.py) asks Gemini to stitch split front/back tables into one canonical 22-column table and validates the result; a rejected merge names the rule and line and falls back to the cleaned tables.
4. [mistral_scorecard_parser.py](../../services/mistral_scorecard_parser.py) identifies rows, player selection, and hole columns and returns `ParsedScorecardRows`. It reads both the stitched table and the cleaned raw tables: split halves are grouped into front and back sections by block (headerless tables are voted to a side by their subtotal columns and aligned to that side's header), player rows are paired across halves by ordinal when both halves have the same number of them, the player's name may sit in either label cell, and on to-par cards an unlabeled or mislabeled par row is recognised by its values plus a matching subtotal. When the named row is missing and exactly one player block has no name label, that block is used and the response carries a review warning (`PLAYER_NAME_NOT_READ`), which the current frontend does not display.
5. [scan_assembly.py](../../services/scan_assembly.py) converts parsed rows into a round, structured review notes and confidence. Known-course holes use their numbers and declared layout; incomplete stored hole rows do not truncate scores, and missing course pars can fall back to valid scanned pars. An unknown-course total par requires all 18 pars; missing scores never imply a nine-hole layout. [scan.py](../../api/routers/scan.py) handles request checks, course access, catalog wording, course handicaps and the typed response. "Name is unclear" is returned only when no row carried the given name; otherwise the rows were unreadable.
6. The user reviews/corrects the result. [ScanService](../../services/scan_service.py) handles the separate reviewed-save workflow.

## Diagnostics versus review warnings

`ParsedScorecardRows.warnings` passes through as round-level text in `fields_needing_review`; converting those parser warnings to structured catalog entries remains a follow-up. The current frontend does not display `fields_needing_review`. `ParsedScorecardRows.diagnostics`, the OCR clean-up notes and the merge outcome are internal: each decision or refusal is recorded as one line ("split halves have 6 vs 7 player rows; ordinal pairing refused", "table merge rejected: line 7 has 23 columns, expected 22"), logged by the router as one `Scan diagnostics` line per stage, attached to `ScanExtractionError.diagnostics`, and printed under each case in the eval report. They never enter the API response or failed-scan reports.

## Review notes and confidence

[scan_assembly.py](../../services/scan_assembly.py) returns `ScanNote` values for missing or misread strokes, to-par scores without known par, corrected signs, invalid putts/shots-to-green and conflicting breakdowns. The router formats them with `SCAN_REVIEW_NOTES` in [messages.py](../../api/messages.py), preserving parser warnings first and any missing-name warning last. Invalid raw or converted strokes become unknown with a misread note instead of silently becoming blank.

Strokes confidence is 0.2 when missing, 0.7 when a present score has a breakdown-conflict note, and 0.9 otherwise. A sign correction keeps its note but not a lower confidence: on the 26 captured cards every correction was right (10 of 10), while 43 of 55 conflicting breakdowns had a wrong score. Putts and GIR confidence are unchanged; each hole's overall score remains the minimum of strokes and putts confidence, and every review note still counts towards the round penalty. These are heuristic review flags, not calibrated probabilities. The frontend already rings non-high strokes amber, so conflicting breakdowns are now highlighted. It does not show the note text, including the explanation for a misread score or missing player name.

Unknown-course nine-hole scan layout, explicit scan-response coverage, and nine-hole course handicaps on scanned tees remain follow-ups.

## Observation versus accepted value

The course name is never read from the scan: a card may not show it, so the user picks or enters it during review.

OCR output is evidence, not verified golf data. Hole identity, raw/to-par score interpretation, unknown cells, and optional field suppression affect what can safely be assembled. Missing cells must not shift later holes. Provider calls, parsing, normalization, domain validation, and persistence are separate responsibilities even where current code mixes them.

## Planned representation change

A hole-centric parsed representation could make related observations easier to follow than parallel arrays. That is a maintainability proposal, not implemented architecture or a demonstrated accuracy improvement. Preserve current contracts first; correctness changes need their own evidence and decisions.

The main regression gate is end to end: `tests/integration/test_api_e2e.py` runs real Mistral captures (`tests/integration/fixtures/mistral/`) through `/api/scan/ocr` and `/api/scan/extract` with the merge skipped and grades them against the large eval manifest, with a per-case minimum. Deterministic unit tests for the individual rules are `test_mistral_ocr_service.py`, `test_mistral_scorecard_parser.py`, `test_gemini_table_merger.py`, `test_scan_assembly.py`, and `test_scan_router_helpers.py`. Live evaluation through `scripts.quick_scan_eval` uses provider credits; ordinary documentation/unit checks do not require it.
