## `analytics/stats.py`

### Overall assessment and scope

The user considers most functions reasonably structured, with some sections needing cleanup. The review agrees that many individual metric functions are focused. The main organization concern is the large achievement builder and repeated aggregation/response construction. This is not a recommendation to rewrite the entire module.

Reviewed the full 1,702-line file on `models-domain-refactor`. No application or test files were changed. Behavior-preserving cleanup should be planned separately from the correctness fixes and product decisions below. The earlier API findings remain linked context, not completed fixes.

### Cleanup: greyed-out helpers at lines 318–339

The module-level `_first_round_with_putts_below`, `_round_gir_percentage`, and `_first_round_reaching_gir` have no callers found in the repository. `notable_achievements()` defines local copies at lines 531, 559, and 566; calls inside that function bind to those local definitions and shadow the module-level helpers. All three duplicate pairs have identical ASTs, including their signatures and bodies.

This explains why the top-level copies can appear unused in the editor. The underlying operations are used through the local copies. Later cleanup can keep one authoritative implementation per helper and preserve behavior; greying alone is not sufficient evidence to delete other functions.

### Cleanup: achievement builder and repeated work

- `notable_achievements()` (lines 342–692) combines scoring records, career totals, streaks, home-course records, putting/GIR milestones, and score-break milestones. Lifetime/year and value/event dictionaries repeatedly express the same metric definitions. Smaller builders grouped by responsibility would make this easier to follow without changing the public response.
- `_achievement_hole_rows()` is rebuilt repeatedly for the same rounds, and date sorting/totals are repeated across record and milestone helpers. Consider preparing reusable round/hole observations once within an aggregation call, then using them consistently. No performance benchmark was run, so this is confirmed duplicate work rather than a measured latency problem.
- `_course_label()` exists, while `_achievement_hole_rows()` and other functions repeat course-name fallback logic. GIR percentage also appears in multiple places. Consolidate only calculations whose eligibility and denominator contracts are actually equivalent.
- `Any` and loose dictionaries make event/response shapes difficult to check. `_milestone_event()` declares string values but can return `round_id=None`. Tighten internal typing while preserving the serialized contract; coordinate actual schema changes with the API/frontend.
- Constants such as achievement thresholds and yardage buckets could have one authoritative definition. The API's duplicate empty response was already reviewed separately.

### Confirmed issue: missing-data denominators disagree

- `putts_per_gir()` (line 1063) divides by GIR holes with recorded putts. `overall_putts_per_gir()` (line 1106) divides the same observed putt sum by all GIR holes, including those with unknown putts. Reproduced on the same single round: two GIR holes, only one with two recorded putts, produce per-round **2.0** versus overall **1.0**. `rounds_with_data` also counts a round with GIR but no observed putts. Align observed denominators and expose coverage without treating unknown putts as zero.
- `overall_gir_percentage()` (line 1132), `gir_per_round()` (line 1030), `round_summary()` (line 695), and achievement GIR percentage count all numbered hole entries in the denominator. Reproduced: two known GIR hits plus one unknown GIR yield **66.7%** and one reported missed green, although no miss was observed. Define the observed-GIR denominator and distinguish unknown observations from misses.
- `three_putts_per_round()` (line 805) returns **0.0%** for a round with zero putt observations. This is distinguishable internally through `holes_with_putt_data=0`, but a consumer can interpret it as measured zero; the current frontend percentage type is non-nullable. Decide the representation for no observations and coordinate consumers before changing behavior.
- `metric_comparison_snapshot()` (line 719) excludes null values from averages but reports the number of rows as `sample_size`. Reproduced: two window rows, one non-null metric, display sample size two while averaging one value. Primary and secondary metrics can have different observed sample sizes. Clarify whether this field means window size or observation count, and expose both when needed.

### Confirmed issue: incomplete rounds enter round records

`notable_achievements()` and `_first_round_below()` use every non-null partial score total without round-completeness or intended-format checks. Reproduced: one scored hole totaling **4** becomes the lowest round and unlocks break-60. With a linked par-72 course it also becomes the first round under par.

`_achievement_hole_rows()` includes numbered entries with no strokes, so `total_holes_played` can count unread placeholders. Reproduced: one scored hole plus one numbered unscored entry reports two holes played. `_valid_hole_scores()` checks only that the hole number is present; its name does not imply a scored, unique, or eligible hole.

These findings depend on the shared round-format/completeness rules already recorded in the parent and Models notes. Define eligible round records separately from usable partial hole-level observations. This remains a future behavior fix, outside structural cleanup.

### Confirmed mismatch: scrambling rule and implementation

`scrambling_per_round()` (line 847) documents success as `strokes <= par`, but implements `strokes == hole.par`. Reproduced: a missed-GIR birdie records one opportunity and zero successes. Existing tests deliberately encode exactly-par behavior, so passing tests do not resolve the conflict. Confirm the intended rule before modifying code or expected results.

### Confirmed issue: inconsistent par/course dependence

`scrambling_per_round()`, `average_score_when_gir_vs_missed()`, and several per-hole aggregations require a linked course and read `course.get_hole()` directly. Other functions use `Round.get_hole_par()` and support unlinked rounds with `par_played`.

Reproduced: an unlinked par-4 score with known strokes/GIR is counted as a par by the score distribution but contributes no scrambling opportunity or GIR/missed-GIR average. Course-specific charts have a legitimate caller filter; the shared question is which calculations actually require course identity versus only known per-hole par. Align par authority and fallback with the pending Models decision, without silently changing historical par precedence.

`average_putts_by_hole()` (line 1455) additionally discards an entire round if any numbered entry lacks putts. Reproduced: a known two-putt hole is excluded because another hole has unknown putts. Decide whether per-hole averages should retain observed holes; whole-round total completeness and per-hole observation eligibility need not be identical policies.

### Confirmed crash: missing course hole in handicap scoring

`scoring_vs_hole_handicap()` (line 1308) dereferences `round_obj.course.get_hole(...).handicap` without checking whether the hole exists. A linked course with an empty/incomplete hole list plus a numbered score raises **AttributeError** before the subsequent `par is None` guard can skip it. The analytics API calls this function directly. Guard missing course holes and define fallback to `handicap_played` consistently with par authority.

### Confirmed issue: date/window handling

- `notable_achievements()` uses naive `datetime.now()` and compares directly with model dates. Timezone-aware model dates are accepted, but mixed awareness raises **TypeError**. Reproduced with a UTC-aware round and a naive reference date. Establish date normalization with API/persistence; do not infer that every current database row triggers this case.
- Milestone counters format a datetime as `YYYY/M/D`, parse it back at midnight, and compare it with the original datetime cutoff. Reproduced: a round two hours inside the cutoff day counts as a round in the one-year window but contributes zero putting milestones because its time was lost.
- Milestone counters check `dt >= cutoff` without also checking `dt <= now`. Reproduced: a future-dated round contributes zero rounds to the window but eleven score-break records to its supposedly one-year milestone count. Use a consistent window policy across rounds and events.

### Confirmed event metadata omission

`_first_round_under_par_event()` (line 199) constructs a new dictionary from `_milestone_event()` but drops `round_id`. Reproduced: the result contains score/date/course only, while other milestone events retain round identity. The career UI and milestone route use this identity for round navigation. Preserve it in the eventual fix.

### Ordering, classification, and tee-selection decisions

- Achievement streaks consume rounds in caller order, while first/best events sort by date. Reproduced: the same dated rounds produce a longest birdie streak of two versus three when reordered. Current inspected API callers supply chronological rounds, so this is an implicit contract and reuse risk rather than a demonstrated API ordering failure. Document/enforce ordering and decide how streaks handle round boundaries, unplayed holes, and unknown observations.
- `_score_type_from_to_par()` intentionally groups eagle-or-better and quad-bogey-or-worse for charts. That bucket is also used by `total_eagles`/`first_eagle` achievements. Reproduced: an albatross enters the eagle total and first-eagle milestone. Decide whether achievements mean exact scores or grouped chart categories; do not remove intentional chart grouping during cleanup.
- `_resolve_tee_for_yardage()` (line 33) can fall back to a course's only populated tee even when the stored tee label names a different tee. Reproduced: a round selecting Red uses Blue yardages when Blue is the sole populated tee. The fallback is explicit existing behavior, but yardage accuracy depends on approving that inference. Decide when to return unknown versus a fallback; keep this separate from rearranging helpers.
- Per-hole functions document a same-course input set, and current course-analytics callers filter by course. Preserve that contract or enforce grouping explicitly during future reuse; mixing identical hole numbers across courses is not evidence of a current caller bug.

## `analytics/goals.py`

### User assessment and cleanup direction

The user finds the code condensed and wants the numerical logic checked. The proposed cleanup is to give three-putts, blowup holes, yardage, home-course, GIR, scrambling, and par-five recommendations their own functions. The file is 238 lines, but almost all behavior is inside `goal_report()`, which combines seven distinct calculations with narrative formatting, eligibility thresholds, percentage conversion and ranking.

This is a useful function-level separation within the existing file. A possible shape is one builder per saver, returning a saver or None; `goal_report()` would prepare shared inputs, calculate the score summary, collect results, and rank them. Shared percentage/formatting rules can have a focused helper. Preserve the current public response during a cleanup extraction, including omission of unavailable recommendations and tie ordering. ### Confirmed bug: known zero GIR is replaced by a default

At line 185, `gir_data.get("gir_percentage") or 33.0` replaces an actual **0.0%** with **33.0%**. It should distinguish unavailable data from a measured zero.

Reproduced with a complete eighteen-hole synthetic round that missed every green: the scrambling estimate is **1.81** strokes, based on 12.06 inferred misses. Applying the existing 15-percentage-point improvement cap to eighteen observed misses would give **2.70**. This example checks the current formula's internal consistency, not whether that improvement cap is calibrated.

### Confirmed issue: round format and observation coverage are inconsistent

- Scrambling hardcodes eighteen holes at line 186. A nine-hole round with nine known missed greens still returns **1.81**, while nine observed misses times the same 0.15 cap would give **1.35**. Use an agreed round format and observed opportunities rather than silently treating every round as eighteen holes.
- The score summary excludes rounds with no total, while yardage and par-five estimates divide by `len(rounds)` regardless of usable observations. Reproduced: adding an empty round leaves the average and goal gap unchanged but halves the yardage estimate from **18.0** to **9.0**. Define which rounds contribute to each numerator/denominator and expose evidence coverage.
- Three-putts uses any round with one or more known putt values as a per-round sample; partial putt coverage can look equivalent to a complete observed round. Scrambling averages round percentages equally, despite potentially very different opportunity counts. Decide the intended weighting/coverage policy before changing it.
- The score summary accepts any partial total and mixes nine/eighteen-hole totals. Reproduced: one four-stroke hole yields average/best score **4**, goal **89**, gap **-85**, and `on_track=True`. This depends on the existing shared completeness/eligibility work; it is outside structural cleanup.
- `overall_gir_percentage()` currently treats unknown GIR observations as missed greens, and `scrambling_per_round()` currently implements exactly par rather than its documented par-or-better rule. These previously recorded Stats findings propagate into this report. Fix the authoritative metric contracts rather than compensate independently in each recommendation builder.

### Estimates need explicit assumptions and units

The literals include 45% GIR, 50% scrambling, a 0.6-stroke GIR value, a 15-percentage-point scrambling cap, fixed blowup-conversion limits, a 0.3 par-five target and 0.8 cap, minimum sample sizes, visibility cutoffs, and percentage caps. The file provides no source or calibration data for claims such as an average GIR of about 45% or what is "realistic" for a given player. Some numbers are display policy, some are evidence requirements, and others are predictive assumptions; document and name them according to those roles. This review does not claim a different population average is correct.

- The GIR comment equates a ten-percentage-point improvement with one additional GIR per round. On eighteen holes, **18 × 0.10 = 1.8 greens**, so that conversion does not match its stated units. The formula uses increments of ten percentage points times 0.6, without specifying a round-length basis. Decide the intended hypothetical change and express it consistently.
- Scrambling caps improvement at fifteen percentage points, but its copy describes savings from reaching 50%. For a player starting at 0%, the estimated change is 0% to 15%, not 0% to 50%. Align the wording with the actual scenario after the zero-value bug is fixed.
- The par-five comment describes cutting 0.5 strokes per hole, while the formula uses `min(average_to_par - 0.3, 0.8)`. Explain or correct the assumption rather than preserving misleading commentary through extraction.
- The yardage and home-hole recommendations label all observed strokes above par as potential savings without defining an attainable improvement target. That measures current loss relative to par; it does not establish that all loss is recoverable. Keep measured performance distinct from predicted savings.
- There is no effort/cost model, although the module/docstring describe highest ROI. Current sorting ranks estimated strokes only. Describe it accordingly or define the intended ranking evidence in a separate behavior decision.

### Confirmed sampling and selection concerns

- The home-course gate checks five input rounds, not five observations on the selected hole. Reproduced: five home rounds, with the worst hole observed only once at four over par, produce a **4.0**-stroke saver with `sample_size=1`. Decide the minimum per-hole evidence and how the home-course sample relates to the general report's recent-round sample.
- Yardage chooses the bucket with the highest average to par, then estimates per-round loss. Those are different ranking bases. Reproduced: a rare bucket averaging +2 costs **2.0** per round and is selected over a frequent +1 bucket costing **10.0** per round. Decide whether the card means worst per-hole performance or greatest per-round opportunity; neither definition should be inferred merely from the function's name.
- The API supplies the main report from a recent `limit` (default fifty), while home-course history is separately capped at five hundred. This can compare recent goal gap with older home-course behavior. Define compatible sample/timeframe meanings and keep achievement/all-history semantics separate from improvement analysis.

### Confirmed copy/number inconsistencies

- Fractional blowup counts use integer formatting. Reproduced: one triple across ten rounds produces **0.2** savings, but the detail says converting **0 doubles and 0 triples** saves those strokes. Display per-round averages with appropriate precision.
- The three-putt helper counts all holes with three or more putts, while this builder assumes one saved stroke and calls every observation a three-putt. Reproduced: one four-putt hole yields **1.0**, although converting that hole to two putts removes two strokes. Either label the estimate as a conservative 3+-putt opportunity or measure excess putts; do not change the intended estimator silently.
- Triple-plus grouping similarly assigns two saved strokes to all triple-or-worse holes. Decide whether this is an explicit conservative estimate or an exact conversion to bogey.
- Percentages are computed from the unrounded positive gap, capped at 999 in the response, while detail text uses the uncapped value and the current UI caps bars at 100. Near the target, a displayed gap of **0.0** can coexist with `on_track=False` and thousands of percent in detail text. Align precision, wording and display limits without discarding the underlying calculation.
- Recommendations overlap: a three-putt can also be a blowup on a par five, in the worst distance bucket or on the home-course hole. Individual percentages are not independent shares that can be summed into guaranteed savings. The response does not sum them, but documentation/UI wording should make the interpretation clear.

### Goal semantics and verification

`on_track` currently means the scoring average meets the threshold. It is distinct from achieving the goal in any single round, which can be derived from best score; do not flag those as contradictory without tracing the consumer. The scope of best score is the provided sample, not automatically all history. Earlier API review notes already record that distinction.

## `analytics/handicap.py`

### Overall assessment and scope

The user considers this file generally well structured. The dedicated review found seven functions across 248 lines, with understandable boundaries between differential calculation, seed eligibility, index calculation, trend generation, and annotation. There is no strong structural reason to split this module. Changes below concern correctness, shared contracts, and small cleanup; no application/test code was edited.

The basic fewer-than-20 selection table matches the [USGA Rule 5.2a table](https://www.usga.org/content/usga/home-page/handicapping/roh/Content/rules/5%202a%20For%20Fewer%20Than%2020%20Scores.htm). Selecting the lowest eight of the latest twenty is also the base procedure in [R&A Rule 5.2b](https://www.randa.org/en/roh/the-rules-of-handicapping/rule-5). Those correct pieces do not establish full WHS compliance.

### Confirmed issue: partial and malformed rounds become eligible

`_get_differential_for_round()` (line 39) infers eligibility from the count of non-null strokes and numeric thresholds (`course_rating >= 50`, `par >= 50`). It does not establish the intended hole format or validate unique, numbered, complete scores.

- Reproduced with three separate unrated one-hole rounds: each has five strokes and `par_played=4`, receives differential **1.0**, and the three-round index is **-1.0** after the table adjustment. A partial observed score is being treated as an eligible round.
- Reproduced with a rated round containing eighteen stroke entries but every hole number missing: it still receives differential **18.0**. Duplicate numbered entries are likewise not checked by this eligibility path.
- The code has a low-rating branch apparently intended for nine-hole ratings, but `Tee` and `UserTee` currently constrain course ratings to 55–85. That intended representation cannot be expressed through the normal models.
- Unrated nine-hole totals are accepted directly as score-to-par, while nine scored holes using an eighteen-hole rating are rejected. This does not establish one coherent nine-hole handicap contract.

Coordinate with the recorded Models round-format, completeness, par/tee authority, and rating decisions. This is a future behavior fix, separate from cleanup. Under the current USGA nine-hole procedure, nine-hole differentials are combined with an expected score to obtain an eighteen-hole differential; scores for fewer than nine holes are not acceptable. See [USGA Rule 5.1b](https://www.usga.org/handicapping/roh/Content/rules/5%201b%20Calculation%20of%20a%20Score%20Differential9Hole.htm). Implementing that broader behavior is not authorized by this review.

### Confirmed issue: displayed differentials and index use different precision

`score_differentials_per_round()` and `handicap_trend()` round differentials for output, but `handicap_index()` selects and averages unrounded values. `annotate_used_in_hi()` ranks the rounded output, introducing a second selection basis.

- Reproduced with twenty valid rated rounds: seven raw differentials of **10.848**, one of **11.752**, and twelve higher values. The module returns index **11.0**; the average of the eight displayed, tenth-rounded differentials rounds to **10.9**. The core calculation and displayed record disagree.
- Reproduced with raw differentials **9.96** and **10.04**: both display as 10.0, and annotation selects the newer one as a tie even though the current index calculation uses the genuinely lower raw value.
- Python `round()` is not an explicit WHS tie-rounding policy. A rated score of 87, rating 72, and slope 100 produces raw differential **16.95**, displayed as **16.9**; nearest-tenth with .5 upward gives **17.0**.

[USGA Rule 5.1a](https://www.usga.org/content/usga/home-page/handicapping/roh/Content/rules/5%201a%20Calculation%20of%20a%20Score%20Differential18Hole.htm) specifies rounding the eighteen-hole differential to the nearest tenth with .5 upward. Use one explicit precision/rounding contract for calculation, selection, annotation and display. Preserve any unrounded values needed by separately implemented rules rather than mixing roles silently.

### Confirmed issue: used-round flags do not describe the calculated index

`annotate_used_in_hi()` (line 217) independently selects rounds from the provided display entries. It does not receive the eligibility/seed decisions or round identities selected by `handicap_index()`.

- Reproduced with a full history of eight differential-0 rounds followed by twelve differential-20 rounds: the actual current index is **0.0**, using the older eight. Displaying only the newest five causes `_build_handicap_trend()` to mark one differential-20 round as used and sets threshold 20, although none of those displayed five contributes to the index.
- Reproduced with seed 15, eight pre-reset differential-20 rounds, and twelve post-reset differential-30 rounds: the seeded index is **30.0**, excluding the older rounds. Annotation instead marks all eight excluded pre-reset rounds as used.

Use the same full calculation context to determine membership, then attach those flags to whichever rounds are displayed. Decide how manual seeds affect history and labels before changing the public result. The earlier API review already identified the slicing issue; this engine review confirms the underlying independent-selection problem.

### Confirmed caller mismatch: seed and history context

- `api/routers/users.py::get_user_handicap()` and `services/ai_service.py` pass the user's manual handicap and reset date. Dashboard/analytics calculation and `_build_handicap_trend()` omit those inputs. Reproduced at the engine boundary: no rounds yields **None** without a seed and **18.2** with a seed of 18.2. Different screens can therefore show different handicap values for the same user.
- Dashboard and the user-handicap endpoint fetch only twenty raw rounds; the latter inherits the repository default limit. Analytics fetches `limit + 19`, with course/date filters also applied. Twenty raw rounds do not guarantee twenty eligible differentials, and display filtering changes the calculation history.
- Reproduced with three eligible rounds followed by nineteen ineligible rounds: full history calculates an index, while the latest twenty raw rounds contain only one eligible round and return **None**.

Centralize the intended seed/history policy across API and AI callers. Keep handicap history separate from chart display filtering and acquire enough eligible observations for the chosen contract. These are cross-layer fixes, not local renaming cleanup.

### Product decision: estimated handicap versus complete WHS calculation

The module and user endpoint describe their results as WHS Handicap Index calculations. The implemented score-to-par fallback and seed-improvement filtering are app-specific policies. The fallback docstring's claim that unrated data keeps the index moving correctly is stronger than the implementation establishes.

The current calculation also uses raw total strokes and has no inputs/application for adjusted gross score, PCC, low-index soft/hard caps, or exceptional-score reductions. Persistence has adjusted-score/differential columns, but the current domain/calculation path does not use them. The [USGA differential formula](https://rulesworkshops.usga.org/content/usga/home-page/handicapping/world-handicap-system/world-handicap-system-usga-golf-faqs/faqs---what-is-a-score-differential.html) uses adjusted gross score and PCC; [R&A Rule 5](https://www.randa.org/en/roh/the-rules-of-handicapping/rule-5) describes the additional safeguards.

Decide whether the app promises an estimate, a documented WHS-based subset, or the full applicable handicap procedure. Do not silently add the missing mechanisms, remove the fallback, or claim that zero PCC is wrong for every round. This review is not an official handicap certification or implementation plan.
