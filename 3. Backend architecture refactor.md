Recording this direction does not approve a final schema, implementation plan, or scanner rewrite.

## Per-hole parsed objects instead of parallel field arrays

### Clarified intent

Tucker's proposed direction is to organize parsed scorecard data around each hole. The user clarified that the motivation is **cleanliness, readability, and easier management**, rather than a new image-recognition algorithm or guaranteed scan-accuracy improvement.

Use one reusable class, provisionally called `ParsedHole`, with one instance per hole—not separate class definitions for hole 1, hole 2, etc. The class name and final fields remain planning decisions.

The current parallel arrays require callers to mentally associate `score_row[i]`, `putts_row[i]`, `shots_to_green_row[i]`, and `par_row[i]` with the same hole. A hole-number-keyed collection would make that relationship explicit and let callers inspect the related values together.

### Existing architecture

- `services/mistral_scorecard_parser.py` identifies player/field rows and already maps hole-header columns in its `2d_column` path. It returns `ParsedScorecardRows` with separate field arrays, generally padded to 18 positions.
- `api/routers/scan.py::_build_round_from_parsed_rows` associates these arrays by index, converts score conventions, validates values, and constructs the per-hole response.
- The domain `HoleScore` and the stored/API hole-score records are already hole-centric. The proposed class has a distinct purpose only if it represents parsed observations before final domain conversion, including raw values and uncertainty as needed.

Rows and columns remain complementary: rows establish player and field identity; columns establish hole identity. Making the output hole-centric does not mean removing row detection or demanding that Mistral emit a different physical table layout.

### Proposed boundaries

1. **OCR adapter:** preserve the source structure needed to identify cells; provide recognized text, not unquestioned domain truth.
2. **Parser:** associate source cells with the player, field, and hole; return parsed-hole observations and unresolved ambiguity.
3. **Assembly/business logic:** convert to-par scores using the appropriate par, enforce established bounds, and perform separately approved derivation/validation.
4. **Domain/persistence/API:** continue using the existing round and `HoleScore` contracts unless a distinct change is explicitly approved.

Keep course-wide metadata, tee configurations, subtotals, and player/block context separate rather than forcing every scorecard element into a hole object. Assess whether any row-level helper types are still useful internally; they need not be the downstream representation.

### Reliability constraints

- A class alone does not fix OCR transcription, player selection, missing cells, column shifts, or front/back block alignment. Do not claim an accuracy increase from reorganization alone.
- Row arrays already depend on correct hole associations; per-hole objects do not introduce that dependency.
- An unreadable value with an established position can remain unknown. A preserved empty cell must not shift later values. If position itself is ambiguous, do not invent a hole assignment.
- Optional fields should preserve unknown data separately from explicit zeros. Distinguish scanned values from derived values when derivation is introduced; decide the exact provenance representation during planning.
- A populated field, a valid numeric range, or matching golf arithmetic does not prove that the source cell belongs to the right hole.
- Logical per-hole objects require no perfect image centering. Pixel-level column detection, cropping, deskew/perspective correction, and per-hole provider requests are **not part of this recorded refactor direction**.

### Implementation direction for later planning

Start with a behavior-preserving representation change: same accepted/rejected inputs and external outputs, clearer internal structure. Keep OCR changes, HTML span handling, alignment repairs, recovery-rule changes, confidence calibration, and nine-hole product behavior separate and independently reviewable.

Before adding a new type, compare its responsibilities with `HoleScore` and existing parsed types. Avoid duplicating domain/request schemas merely to relocate them. A dedicated parsed type is reasonable when it retains raw score convention, source observations, or unresolved data that the final domain type cannot express.

Use an adapter to retain existing API/frontend/persistence contracts. The frontend-prefetched `ocr_text` path must remain equivalent to server-side OCR. No database migration or frontend refactor is inherently required by the internal representation change.

### Files to review

- `services/mistral_scorecard_parser.py`: parsed types, header maps, row/player selection, split-section assembly, field suppression, and 18-position helpers.
- `api/routers/scan.py`: parsed-to-domain assembly, raw versus absolute score conversion, confidence/warning behavior, and both OCR entry paths.
- `services/mistral_ocr_service.py`, `services/gemini_table_merger.py`: input contracts and retained/lost structure; review without bundling an algorithm rewrite into this refactor.
- `models/hole_score.py`, `models/round.py`: existing domain responsibilities and compatibility.
- `api/request_models.py`, `api/schemas.py`, `services/scan_service.py`, `database/converters.py`: downstream contracts; change only if required by the approved boundary.
- `frontend/src/types/scan.ts`, `frontend/src/lib/scanUtils.ts`, and scan hooks: compatibility inspection, not an approved frontend change. Estimated frontend values are not OCR ground truth.

### Verification direction

- Compare old/new parser and round-builder outputs on frozen valid, incomplete, ambiguous, split-table, and named-player fixtures.
- Preserve intentional rejection, suppression, warnings, raw/to-par interpretation, and current nine-hole behavior during the first representation-only change. Document known bugs for separate fixes rather than silently changing them.
- Add behavior tests for related fields remaining attached to the correct hole, blank positions, and front/back hole-number identity.
- Relevant deterministic tests: `tests/test_mistral_scorecard_parser.py`, `tests/test_scan_router_helpers.py`, `tests/test_score_sign_disambiguation.py`, `tests/test_mistral_ocr_service.py`, `tests/test_gemini_table_merger.py`, and `tests/test_quick_scan_eval.py`.
- Any later accuracy claim needs a broader labelled image/capture comparison, not just passing unit tests or cleaner types. Paid provider evaluation remains separate.

### Open decisions

- Exact parsed-hole fields, container, module location, and compatibility adapter.
- Which raw tokens/source associations and uncertainty states the intermediate type should retain without expanding the public API.
- Whether lightweight typed rows remain useful as internal classification helpers.
- Sequencing against unmerged parser/recovery work and the consistency review. Reinspect current main/PR state before implementation.
