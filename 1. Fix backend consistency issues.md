## October 15, 2026 — model contracts implemented; integration pending

See the [Models implementation summary](<1. Fix backend consistency issues - Models.md>) for exact fields, helpers and remaining dependencies. The approved decisions are now implemented and regression-tested in `models/` only:

- Explicit course layout and intended round coverage, including standalone/front/back nines; unique hole identities determine completeness, not counts. Intentionally unplayed, unread and unknown are distinct.
- Historical accepted per-hole par first; partial strokes and to-par compare the same holes. Child observations are authoritative, missing stats stay unknown, and safe updates/serialization prevent stale summaries from returning.
- Shared yardages: integer 0–1,000, hole numbers 1–18, omit unknown entries, reject aliased keys, validated replacements instead of in-place edits. No manual-yardage UI.
- Positive finite course ratings with explicit matching rated coverage; slope 55–155; no magnitude inference or automatic halving. Optional ratings/tee selection do not prevent otherwise valid basic scoring.
- Separate eighteen-hole goal `scoring_goal` (18–270) and nine-hole goal `scoring_goal_nine` (9–135). Net means gross minus the applicable handicap allocation; no guessed handicap inputs. Condor is exactly -4, albatross -3, with exact numeric labels outside named results.
- Model-only structural readiness helper requires complete course pars and yardages for at least one identified tee, plus a selected tee if supplied. It is NOT course verification or an end-to-end save gate.

Before the integrated backend reaches `main`, later API/Services/Database/Analytics branches must carry/persist the new metadata and goals, align constraints and unknown-value normalization, update format-aware statistics/handicap eligibility, and wire source verification plus atomic course/round saves. Known-course resolution stays DB-first without routine provider credits. New-course provider verification/yardage fallback is required; incomplete or unverified required course data must save neither course nor round and offer re-scan/retry. Optional player statistics may remain missing. Existing DB rows are not certified verified by this change.

Domain branches merge into `backend-refactor`; the finalized integration branch merges into `main`. No frontend, provider, live database, migrations or production changes are included in this model branch. The earlier findings below remain review evidence for later domains.

## Shared rules and changes

### Per-hole yardage bounds

**User decision:** per-hole yardage must be between 0 and 1,000 yards, inclusive, everywhere. Align Models, API, and Database, with a migration for existing database constraints.

**Confirmed changes needed:** `Tee` already permits zero but caps yardage at 700; API validation and the normalized yardage table currently require 50–700. `UserTee` lacks corresponding model validation. Unknown yardages remain distinct from an explicit zero; their null-versus-omitted representation is still undecided.

### Course ratings and nine-hole support

**Confirmed mismatch:** Models and API restrict course rating to 55–85, while handicap logic has a shorter-round path using ratings below 50. Database constraints and scan normalization also need alignment.

**Decision needed:** represent the rated hole format and define appropriate supported ranges. Apply the rule across Models, API, Services, Database, and Analytics.

Complete nine-hole course par must be calculable from its holes. Expected hole numbers and uniqueness must be explicit rather than inferred solely from entry counts.

### Round completeness and partial totals

**Confirmed issues:** completeness is inferred from entry count; partial strokes may be compared against full-course par; different totals handle missing observations differently.

**Deferred direction:** establish the intended hole set, require unique scored holes for completeness, and distinguish partial observations from complete totals. A skipped hole does not change the course's par.

**Decisions needed:** how to represent intentionally unplayed versus unread scores; whether and how partial totals are displayed; eligibility of partial and nine-hole rounds for averages, goals, milestones, and handicap calculations. Coordinate Models, API, Services, Database, and Analytics.

### Analytics eligibility, history scope, and response contracts

Stats-router review reproduced partial scores being treated as round records/averages, unknown GIR being counted as zero, and different weighting policies across percentage KPIs. Establish metric-specific eligible rounds/observations and consistent denominators; support hole-level analysis without treating every partial subtotal as a complete round result.

Fixed query caps currently feed total/lifetime/first-achievement results and can exclude valid older rounds from comparisons. Define all-history, selected-window, and improvement-analysis scopes explicitly and use queries appropriate to each. The large empty analytics response has drifted from the populated schema; share typed defaults and authoritative milestone thresholds.

Handicap callers disagree on seed inputs and fetch raw history that may omit needed eligible rounds. Filters and display slicing also change calculation history or used-round flags. Centralize calculation context and separate it from display scope, coordinating API, Analytics, Database, and tests. The API and Analytics child files record the dedicated reviews and evidence.

AI-service review reproduced negative handicaps selecting the highest-handicap benchmark, missing putt observations appearing as improvement, and scrambling being labeled as up-and-down. Its savings estimates also hide fixed opportunity assumptions, and duplicated par/putting aggregation disagrees with Analytics and the approved historical-par rule. Coordinate metric eligibility, benchmark provenance, units, and response labels across Services, Analytics, Models, and frontend consumers. Detailed reproductions and unresolved ranking/calibration policies are in the [Services review](<1. Fix backend consistency issues - Services.md>); no service fixes are implemented.

### Par and tee authority

**Confirmed issue:** a linked course with missing par blocks fallback to available `par_played`. Related methods apply different par-resolution rules.

**Decisions needed:** historical par versus current course par precedence, and custom user tee versus matching course tee precedence. `tee_box` already represents a player's selection. Tee edits must keep the authoritative selection consistent.

Centralize resolution rules and apply them consistently to model methods, responses, persistence, and analytics.

### Hole-score validation and field meanings

**User decision:** retain per-hole limits everywhere: strokes 1–15, putts 0–10, and shots to green 1–10.

**Confirmed gap:** shots to green can exceed total strokes. Check this when both values are known.

**Decisions needed:** whether shots to green includes penalties and all non-putting strokes before requiring `shots_to_green + putts == strokes`; what `net_score` represents and its supported range. The current domain/database net-score bounds differ from unrestricted API integers. Coordinate Models, API, Services, and Database.

### Shared classification and score labels

**Deferred direction:** share backend score classification and a module-level label constant. Analytics may group exact classifications into chart categories separately.

**Recorded naming direction:** albatross matches exactly -3. The upper-end rule is interpreted as names through +4, then exact numeric labels such as `5 over` and `6 over`.

**Decision needed:** treatment of results below -3; rare scores must not be mislabeled as albatross. The Models child file retains the discussion and source reference. Coordinate Models and Analytics, checking exposed API labels during implementation.

### Safe updates, stored summaries, and unknown values

**Reproduced issues:** rejected cross-field assignments can leave an object invalid; direct dictionary mutations bypass assignment validation; supplied totals can remain stale after child data changes.

**Deferred direction:** establish validated updates that preserve the prior valid state on failure, reconcile stored summaries after successful edits, and define aggregate bounds. Unknown yardages also need one representation: API accepts null entries that `UserTee` rejects.

Coordinate Models, API, Services, Database, and Analytics according to each update path. Preserve unknown values separately from known zeros or misses.

**Confirmed round-update behavior:** omitted hole-score fields become null and overwrite existing scoring/statistic fields; par and handicap instead preserve existing values through SQL `COALESCE`. Establish replacement versus field-level update semantics. For field-level updates, merge supplied fields with existing data and validate the final state.

Round-router review also found ignored explicit-null metadata, inconsistent SQL/model summaries, nine-hole completeness changing on edit, invalid inputs or intended 404 responses becoming 500, and separately committed writes within one edit/link operation. Align missing-data semantics and save/edit calculations, translate errors consistently, and make combined operations atomic. Course relinking needs consistent hole references and an explicit policy for historical par/handicap and tee authority. Detailed evidence is in the API child file.

User-router review found the same null-clearing and expected-error inconsistencies in tee updates, plus malformed/null yardages producing 500 and fractional yardages being silently truncated. Linked user-tee course IDs are not checked against course access rules. Share course-reference authorization and typed yardage validation; consider separating profile, tee, and friendship transport responsibilities. Friendship email-sharing policy and repository state-transition concurrency remain follow-ups. Details and verification limits are in the API child file.

### Shared rules and duplicated implementation

**Duplicate classes within the same layer:** `HoleScoreInput` in `api/request_models.py` and `HoleScoreUpdate` in `api/routers/rounds.py` currently have the same fields, bounds, defaults, configuration, and validator. The router location does not justify a separate copy. Reuse the shared request class while their contracts match. If save and update semantics require different types, share their common fields and rules rather than copying them. Separate API and domain classes remain appropriate when they serve different responsibilities.

**Repeated functions and rules:** review functions that independently implement the same intended behavior and consolidate common logic. Candidates already discussed include hole-score consistency validation, score classification and labels, par/tee resolution, round completeness, and aggregate handling of missing data. Shared rules should have one authoritative implementation where practical, with bounds and constants aligned across layers. Preserve differences that reflect actual product behavior, such as exact score labels versus analytics groups.

Keep request parsing, domain behavior, repository mapping, and router orchestration focused on their own responsibilities. Small wrappers delegating to a shared helper are reasonable; repetition alone is not a reason to merge unrelated functions. Compare SQL and model summaries for consistent behavior while preserving useful query optimizations. Detailed evidence and deferred direction are in the [API review](<1. Fix backend consistency issues - API.md>) and [Models review](<1. Fix backend consistency issues - Models.md>).

### Shared API messages and authentication flow consistency

User requested named constants for shared built-in messages. Expand the existing `api/error_responses.py` pattern into one authoritative API message catalog, grouped by purpose/domain, covering repeated failures and success responses. Preserve HTTP/error-category contracts and intentionally generic public auth responses separately from wording. The API child file records examples and migration guidance.

Auth review found registration accepting a private home-course reference, password schemas exceeding the pinned hash helper's encoded-byte limit, token consumption preceding separately committed account mutations, blocking email/hash work, and unreliable link/delivery behavior. Share course-access rules, validate before mutation, and make token/account changes atomic. Coordinate API, notification services, auth helpers, Database, and tests; these are deferred fixes with verification limits recorded in the API notes.

Additional auth follow-up: existing access tokens remain valid after password reset, and logout clears a cookie without revoking bearer tokens. Define the intended session-invalidation policy and test it with any eventual implementation. Verify concurrent one-time-token use in PostgreSQL integration tests; the current sequential test does not establish that guarantee. Ordinary standalone `def` helpers are appropriate and do not themselves require restructuring.

### Scan confidence, completeness, and review evidence

**Priority from the review discussion:** fix the unsupported confidence values as a correctness issue. Moving code into other files alone will not fix their meaning. The extraction router also needs clearer responsibility boundaries; plan that refactor alongside the behavioral fixes after the consistency review.

**User requested direction:** score-confidence categories should use high at 0.90 and medium at 0.70. Threshold changes alone do not establish scan accuracy: the current builder gives every non-null stroke 0.90 and derives overall confidence from value presence and warning count. Separate recognition confidence from completeness, preserve observed versus derived/corrected values, and base review decisions on structured field-level evidence. Missing optional putts/GIR should not lower confidence in readable strokes. Coordinate API, extraction services, and frontend contracts; implementation remains deferred.

Scan assembly also infers hole format from metadata entry count, truncates scans for sparse courses, misaligns back-nine holes, treats partial known par as full course par, and derives GIR before validating shots to green. Apply the shared intended-hole, par-resolution, missing-data, and score-validation policies. The API child file records reproductions and a proposal to move assembly/provider orchestration into focused service stages during refactoring.

Further scan review found temporary-file leaks on failure, cleanup errors masking the primary outcome, synchronous image/file work in async endpoints, PDF validation limited to a prefix check, and misleading/inconsistent failure messages. Anonymous OCR also depends on an available database through optional-auth dependencies despite doing no database work. Coordinate API, extraction services, authentication dependencies, and tests; details and verification limits are in the API child file. Typed partial-data responses, PDF page policy, and provider configuration also need review during the refactor.

### Scoring-goal range

**Confirmed mismatch:** the API requires 50–150, the domain model accepts unrestricted integers, and the database has no equivalent goal-range check.

**Decision needed:** authoritative goal bounds, including how round format affects goal interpretation. Align Models, API, Database, and Analytics; plan existing-data handling before adding constraints.

### Course identity and input normalization

**Investigation requested:** distinguish text validation and display formatting from course identity resolution. Request validation currently changes capitalization; the save service uses provider/database lookup and supports creating user-owned courses from scan data.

**Decisions needed:** canonical display-name preservation, authoritative identifiers, ambiguous matches and location, custom/unmatched courses, and provider-failure behavior. Review whether explicit database course selection should precede name-based provider lookup. Coordinate API, Services, and Database; detailed evidence is in the API child file.

**Additional confirmed API gaps:** selected-tee yardages bypass shared validation, equivalent yardage keys can silently overwrite each other, and duplicate course metadata can pass requests despite database uniqueness constraints. Save inputs also allow all strokes missing, producing zero holes played against a database minimum of one. Align request, model, and persistence rules; do not interpret the existence of these inputs as an approved draft-round contract.

Course-router review reproduced wrong provider-ID attachment across different locations and a 500 response for invalid yardages. Course update par bounds differ from the domain/database, partial course counts conflict with the 9/18 constraint, and update null/conflict handling needs alignment. The API child file records detailed evidence and the affected route/repository boundaries.
