## `services/ai_service.py`

### Overall assessment and current callers

The user finds the structure mostly reasonable, with dense sections and numerical assumptions needing review. Each of the five insight types already has its own method, and comparisons and strengths are separate. Keep those boundaries; there is no demonstrated need to split the file simply because it has 628 lines.

This is a rule-based engine, with no LLM/provider call. `api/routers/ai_insights.py` exposes it through the registered `/api/ai-insights/{user_id}` endpoint. Static tracing finds a frontend `getAISuggestions()` helper but no calls to that helper in the current checkout. Analytics insight cards are independently generated by `useAnalyticsViewModel.ts::computeInsights`; The Lab uses analytics and goal-report data. The user has seen insight UI, but that alone does not establish that the visible cards consume this service. Runtime UI wiring was not inspected. Do not delete the registered service based only on the unused frontend helper.

### Confirmed bug: negative handicaps select the highest-handicap benchmark

`_get_benchmark()` (line 67) only covers nonnegative ranges. Its fallback assigns every unmatched value to `28–54 HCP`, although Models and the endpoint accept negative handicaps down to -10. Reproduced through `generate_suggestions()` with a user seed of **-1.0** and no rounds: the response retains handicap **-1.0** but labels the benchmark **28–54 HCP**. A target of -1 follows the same faulty lookup. Define the supported lower-bound policy explicitly, and test negative, zero, exact band boundaries, 54, and the unrated case. The valid upper endpoint 54 already lands in the intended last band through the fallback.

### Confirmed bug: missing putts can become an improving trend

`_compute_raw()` excludes rounds without putt observations when calculating the three-putt average, but includes their zero `three_putt_count` values in the trend (lines 187–213). In six complete rounds, the first three each contain six three-putts and the last three contain no putt data. The average remains **6.0**, but the trend becomes **[6, 6, 6, 0, 0, 0]**, and the insight reports **improving**. Preserve missing observations in both calculations and apply the same eligibility policy. Partially observed rounds also need a coverage policy before comparing raw counts against full-round benchmarks.

### Confirmed mismatch: scrambling is labeled as up-and-down

`_insight_scrambling()` (line 405), `_build_comparisons()` (line 521), and `_compute_strengths()` (line 562) label `scrambling_per_round()` results as **Up & Down**. Stats exposes a separate up-and-down calculation. In five complete rounds with missed GIR, par scores, and two putts per hole, Stats reports **100% scrambling** and **0% up-and-down**, while this service displays **100% Up & Down**. Choose the intended metric, then align its calculation, benchmark, copy, and labels together. This is separate from the earlier Stats scrambling docstring/rule discrepancy.

### Confirmed issue: stroke-saving claims hide assumptions

- `_insight_putting_quality()` (line 480) multiplies the putts-per-GIR gap by a fixed **8**. A real-model round with one GIR and 2.0 putts per GIR compared with the 1.88 benchmark claims **~1.0 strokes/round**; applying the same gap to the observed one GIR gives **0.12**. Use the player's eligible GIR frequency or state a deliberate scenario assumption; the current personalized wording provides neither.
- GIR copy claims that every **5%** improvement saves one stroke, and scrambling copy claims **10%** saves 1–1.5 strokes. No supporting source/calibration is recorded in this module. Percentage-point gains, relative percentage gains, hole count, and opportunities are different inputs. Establish the estimator and its units before claiming personalized savings; do not replace these constants with new guesses.
- Three-putt counts include holes with **three or more** putts, but the copy equates eliminating each counted event with exactly one saved stroke. State the intended counterfactual, such as reducing a counted event by one putt, or calculate excess putts relative to a specified target.
- Par savings divide qualifying hole counts by **all fetched rounds**, including rounds with no qualifying observations. Align the denominator with the intended complete-round or observed-hole scenario and distinguish nine-hole from eighteen-hole estimates.

### Confirmed issue: duplicated metric rules already disagree

`_par_stats()` and `_par_stats_per_round()` (lines 232–276) repeat par resolution and aggregation. `_putts_per_gir_per_round()` (line 278) independently calculates a trend. An unnumbered scored hole with `par_played` contributes to these helpers while Stats excludes it from the corresponding numbered-hole metrics. A real-model probe returned service par average **+2.0** and putting trend **2.0**, while Stats returned no par row and no per-round putting value.

The service also chooses current course par before historical `par_played`, contrary to the newly approved model authority rule. Use shared eligible-observation and par-resolution rules during integration rather than creating another local variation. These probes used the current model working tree, including its new coverage helpers; they do not imply Models caused the service discrepancy.

Inherited Stats issues also affect the response:

- Eighteen scored holes with all GIR observations missing produce a **0.0% GIR** recommendation instead of an unknown metric.
- Eighteen known GIR hits with putts observed on only two holes at two putts each produce aggregate putts/GIR **0.2222**, while the service's per-round trend is **2.0**. This can produce a false putting strength.

Fix the underlying observed denominators in coordination with Analytics; changing service defaults alone is insufficient. Total putts, round scoring, round format, and handicap-history eligibility must also follow the shared contracts already recorded in the Analytics/API notes.

### Numerical policies needing an explicit decision

- **Benchmark provenance:** document the dataset, cohort, units, round format, and sample sizes behind `_BENCHMARKS`. The Lab has another benchmark table with different values (for example scratch GIR 61 versus 65 here). Those could represent different cohorts; the difference alone does not prove which is wrong or justify merging them blindly.
- **Internal interpretation:** assuming four par 3s, ten par 4s, and four par 5s, the 0–5 band's per-par averages imply **+7.0** over a round while its scoring benchmark is **+3.0**. The 10–15 band implies **+19.2** versus **+12.0**. These illustrative checks show that the metrics cannot be treated as one coherent profile under that course mix without explanation. Different cohorts/course mixes may explain the values; their empirical accuracy was not established in this review.
- **Ranking objective:** par selection uses the largest per-hole gap. A reproduced example selects par 3s with a **2.8-stroke** round opportunity over par 4s with **6.0**, because the par-3 per-hole gap is larger. Decide whether the recommendation prioritizes per-hole weakness or estimated total savings; either needs clear wording.
- **Priority scaling:** multipliers **4, 0.25, 0.15, 2.5, 12** and a cap of **10** compare different metric units. Record why these produce useful cross-category ordering and what happens when several categories saturate the cap.
- **Trend meaning:** the same **0.1** threshold is applied to percentages, putt counts, and stroke averages. Fewer than four observations are called **stable**, and scrambling is always marked stable without a trend calculation. Distinguish insufficient evidence from actual stability; a new status would require response/frontend coordination.
- **Coverage and weighting:** scrambling averages round percentages equally and requires five rounds with opportunities; other insight types can run with one observation. Decide appropriate sample/coverage requirements and opportunity versus round weighting. Missing data must not count toward a sample requirement.
- **Strengths:** a 20% relative qualification threshold is followed by copy displaying the absolute percentage-point difference as “% above benchmark.” Correct the units. The first three qualifying strengths are returned in fixed category order; decide whether that is intentional presentation order or should represent the strongest three.

### Proposed cleanup, separate from behavior changes

- Replace the loosely typed raw-data dictionary with a typed internal result so required fields, observation counts, and units are visible.
- Give policy numbers descriptive names with units and a documented rationale. Keep measured benchmark values separate from ranking weights, sample thresholds, and drill instructions.
- Share par/observation helpers after the cross-domain rules are settled. Preserve the existing one-method-per-insight organization.
- Move repeated static labels and drill copy into small module constants if it makes the calculation methods easier to read. Generic drill distances should not be described as the player's most common approach without supporting player data.
- Remove the unexplained seven-insight slice if it serves no intended contract: only five builders currently run. Separate fetching from pure calculation if that improves meaningful testing. The API already fetches the user before the service fetches it again; clarify ownership without weakening authorization.
- Review the service's dependency on `api.schemas` when defining shared response/internal types during architecture planning; do not introduce a new abstraction solely to move an import.
