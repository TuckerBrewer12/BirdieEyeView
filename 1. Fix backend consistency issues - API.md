## `api/request_models.py`

### Hole-score validation

- `HoleScoreInput` checks putts against strokes but does not check shots to green against strokes. `shots_to_green` already has a 1–10 field bound; the missing check is its relationship to total strokes. Reject shots to green exceeding known strokes, and decide whether to enforce the full score-breakdown equation after defining the field's meaning.
- `net_score` accepts unrestricted integers, while the domain model and database restrict it to -3 through 15. Define the field's meaning and enforce one supported range across layers.
- Preserve the agreed per-hole bounds everywhere: strokes 1–15, putts 0–10, and shots to green 1–10.

### Tee yardages and ratings

- `TeeInput` currently limits per-hole yardages to 50–700. User decision: change the supported range to 0–1,000 yards, inclusive, across all layers.
- `TeeInput.course_rating` and `SaveRoundRequest.tee_course_rating` require 55–85, conflicting with the shorter-round rating path in handicap logic. Define rating format and appropriate bounds consistently.

### Course-name validation and resolution

`SaveRoundRequest._validate_course_name()` sanitizes text to a maximum of 140 characters and calls `normalize_course_display_name()`. Sanitization normalizes Unicode, trims whitespace, replaces newlines, and rejects empty text, control characters, and angle brackets. Display normalization uppercases the first letter of each word and lowercases the rest. Reproduced locally: `TPC PGA Golf Club` becomes `Tpc Pga Golf Club`.

These validators check and format the submitted text; they do not establish course identity or existence. `ScanService._resolve_course()` performs provider and database lookup separately and can create a user-owned course from scan data when no existing course is found.

User requested further investigation of name validation and reliance on provider/database lookup. Preserve appropriate text validation while reviewing canonical display-name handling, stable database/provider identifiers, location and ambiguous matches, custom courses, and behavior during provider failure. The service currently attempts name-based provider lookup before its explicit `course_id` branch; assess whether an explicit selected course should be resolved first. No new course-resolution policy has been approved.

### Additional confirmed input gaps

- **Selected-tee yardage bypass:** `SaveRoundRequest.tee_yardages` lacks the key normalization and bounds checks used by `TeeInput.hole_yardages`. Reproduced locally: `{"19": -20, "1": 1500}` passes request construction. The service can later construct `TeeInput` and reject it. Apply the agreed 0–1,000 range and valid hole-number rules consistently at the request boundary.
- **No recorded strokes:** a request with only `{"hole_number": 1}` passes validation. The converter calculates zero holes played, conflicting with the database's 1–18 constraint. Decide whether draft rounds are supported; otherwise require at least one score before saving. This does not establish whether a partially scored round is eligible for analytics.
- **Duplicate course metadata:** duplicate hole numbers are rejected, but duplicate non-null handicap ranks on different course holes and duplicate tee colors such as `Blue`/`blue` are accepted. Course database constraints enforce uniqueness. Apply agreed course-level rules before persistence and account for partial course data.
- **Normalized yardage-key collisions:** `TeeInput` silently collapses distinct keys that normalize to the same hole number. Reproduced locally: `{"01": 350, "1": 400}` becomes `{"1": 400}`. Reject conflicting duplicate representations rather than silently overwriting a yardage.

Also review agreement between the selected-tee fields and `all_tees`: the service prefers `all_tees` when present. Define how conflicting representations should be handled.

The file has been reviewed in discussion; product decisions and cross-layer follow-ups remain open. Implementation is deferred.

## `api/routers/users.py`

### User-tee inputs

- Shared yardage validation currently limits values to 50–700. Apply the agreed 0–1,000-yard range, inclusive, to both create and update inputs.
- Create and update inputs restrict course rating to 55–85. Include them in the nine-hole rating work.
- Yardage validation permits unknown values such as `{1: None}`, but `UserTee.hole_yardages` requires integers. Reproduced locally: the request accepts this dictionary and constructing the domain model rejects it. Establish one representation for unknown yardages before model construction and persistence.

### Scoring-goal inputs

`UpdateUserRequest.scoring_goal` requires 50–150. The domain model accepts unrestricted integers and the database has no equivalent range check. Establish the authoritative goal range and enforce it consistently; no new range decision has been made.

### Organization and shared validation

Reviewed October 3, 2026, interpreting the user's reference to `user.py` as the API router `users.py`. The individual handlers are mostly short, but this module contains profile management, handicap retrieval, user-tee CRUD, friendship workflows, request/response models, validation helpers, and response projection.

Consider separate profile, user-tee, and friendship routers with their existing public URLs retained, and move transport schemas to dedicated API request/response modules. Keep reusable validation and course-access policies shared. Create/update tee schemas have genuinely different required fields, so retain that distinction while sharing common fields and validators. Centralize handicap history/input selection as recorded in the stats-router review. These are proposed refactors, with implementation deferred.

### Missing linked-course access validation

`create_user_tee` checks the URL user against the authenticated user but does not load or authorize `req.course_id`. The repository inserts the supplied reference without checking course ownership; the foreign key checks existence, not access. A user can therefore associate their tee with another user's private custom course. Validate that a linked course exists and is either master/global or owned by the current user, matching the profile home-course check.

A fake-boundary HTTP reproduction returned 201 with an inaccessible course ID and confirmed the route never called `db.courses.get_course`. No private course contents were exposed by that reproduction. A nonexistent course reference instead reaches a PostgreSQL foreign-key failure without route/repository translation; add an appropriate input/not-found response.

### Update semantics and error handling

- Profile updates use `exclude_unset=True`, preserving explicit nulls. Tee updates use `exclude_none=True`, so explicit null ratings are silently discarded. Reproduced: `course_rating: null` results in no rating argument being passed to the repository. Establish clearing rules for nullable fields and apply them consistently; reject null for a required tee name.
- An empty tee update on a missing/foreign tee can return `None` from the repository's no-op lookup rather than raising `NotFoundError`. The response model then fails and produces 500. Handle missing results consistently on both empty and nonempty updates.
- Creation translates `DuplicateError` to 409, but update has no equivalent conflict mapping and its repository leaves PostgreSQL uniqueness failures untranslated. A duplicate-error HTTP reproduction returned 500. Align create/update conflict behavior.

### Yardage normalization and validation failures

The earlier null-yardage mismatch has been reproduced through the route: `{1: None}` passes the request but fails `UserTee` construction outside error handling, producing 500. Choose a shared unknown-yardage representation before construction.

The unrestricted dictionary validator also performs raw `int()` casts. Reproduced: a list value produces HTTP 500 from `TypeError`, and yardage 350.9 silently becomes 350. Equivalent keys such as `01` and `1` can overwrite each other, as in the shared tee validator. Use a typed integer-yardage contract, report malformed values as input errors, and reject conflicting normalized keys. Apply the agreed 0–1,000 range through the shared implementation.

### Access boundaries and friendship follow-ups

Profile read/update, home-course selection, and handicap retrieval check the authenticated user. Tee list/update/delete operations pass that user to ownership-constrained repository calls. Friendship reads use the current user, and status changes pass the actor into repository permission checks. Preserve and test these boundaries when reorganizing routers.

Friendship responses include both users' email addresses in pending/declined/blocked as well as accepted records, and the frontend currently displays them. Confirm the intended sharing policy rather than assuming a friend-code workflow should reveal contact information before acceptance. This is an unresolved product/access policy, not a verified bypass of an existing stated rule.

Friendship creation/status updates fetch the entire user's friendship list to enrich one returned record and fall back to a row missing joined names/emails. Consider fetching a single authorized enriched record. Request-by-UUID to a nonexistent user can reach an untranslated foreign-key error; align expected failure handling. State-transition concurrency and uniqueness are follow-ups for the friendship repository/integration-test review.

Repository calls and schema were read to identify ownership, foreign-key, and error-translation behavior. No live PostgreSQL or external service was called. Existing route tests cover valid profile/tee/friendship paths and selected forbidden/missing cases but do not establish the above contracts.

## `api/routers/rounds.py`

### Duplicated hole-score schemas and missing validation

- `HoleScoreUpdate` has the same fields, bounds, defaults, extra-field policy, and putts-versus-strokes validator as `HoleScoreInput` in `api/request_models.py`; only field order differs. Both lack the shots-to-green-versus-strokes check and accept unrestricted `net_score`.
- Consolidate the common API fields and validation. Reusing one request schema is reasonable while their contracts remain identical; keep distinct create/update schemas with shared rules if their semantics diverge. The domain `HoleScore` still has its own responsibility and should enforce the same underlying score rules.

### Update field semantics

Confirmed by following `update_round` into `database/repositories/round_repo.py:update_hole_scores`: omitted hole-score fields default to `None`, the router constructs a full `HoleScore`, and the repository overwrites strokes, putts, net score, shots to green, fairway, and GIR with those values. Sending only a new putt count for an existing hole can therefore clear its strokes and other recorded statistics. Par and handicap instead use SQL `COALESCE`, preserving existing values when the input is null.

Decide whether each supplied hole is a replacement or a field-level update. For field-level updates, distinguish omitted fields from explicit null, merge with the existing hole, and validate the resulting state before persistence. Sharing request classes alone does not resolve this behavior.

### Repeated code across layers

Share authoritative field bounds, score consistency rules, and par/tee/completeness policies where the behavior is meant to agree. Keep request parsing, domain behavior, database mapping, and endpoint orchestration focused on their different jobs. Small validators already calling `sanitize_user_text` are delegation rather than separate implementations of sanitization.

Round summaries are produced from both full models and SQL summary rows. Review their semantic agreement; retaining a SQL summary path can avoid loading entire rounds. Consolidation should not require removing that optimization.

### Metadata clearing and empty updates

- `update_round` adds metadata only when its value is not `None`. An explicit `notes: null`, for example, is accepted but does not clear the saved note. The same applies to weather, tee box, and played course name. Distinguish omitted fields from intentional clearing.
- `hole_scores: []` is treated as no score update. Define the empty-list contract; it currently cannot remove existing holes.

### Nine-hole completeness and zero scored holes

`update_hole_scores` in the repository sets persisted `is_complete` using `holes_played == 18`, while initial conversion uses `Round.is_complete()`, which can recognize nine scored holes as complete. A nine-hole round can therefore be marked incomplete after a score edit. Align the save and edit paths with the intended-hole policy rather than copying either current heuristic.

The update request permits all strokes to be null. If an update leaves no scored holes, the repository writes `holes_played = 0`, conflicting with the schema's 1–18 constraint. Decide how drafts and intentional score removal work before changing the constraint or rejecting these requests.

### List summaries disagree with model summaries

The list endpoint uses SQL aggregates from `get_round_summaries_for_user`, while the link response uses `summarize_round` on a domain model:

- SQL requires nine known scores before returning a front/back-nine total; the model returns any available subtotal.
- SQL turns entirely unknown GIR/fairway observations into zero, while the model summary returns null.
- SQL uses only linked `courses.courses.par`; an unlinked round with known `par_played` gets null par/to-par in the list, while the model can calculate them.
- SQL's putt total can include putts on unscored holes; the model's putt method considers scored holes only.
- Both paths can compare a partial score with full-course par. Use the same hole set for both sides of a to-par calculation, following the agreed partial-round policy.

Retain efficient SQL aggregation, but make its contract match the model summary and preserve unknown values.

### Error translation

- `update_round` raises an intentional `HTTPException(404)` inside a broad `except Exception` block that translates it into 500. Preserve HTTP exceptions as the link route already does.
- `HoleScoreUpdate` accepts values such as `net_score = 100`; constructing the domain `HoleScore` then fails and becomes a 500 response. Align bounds and return request-validation errors for invalid input once net-score semantics are defined.

### Atomic writes

Score edits and metadata edits use separate repository writes. Scores can commit successfully, metadata can then fail, and the endpoint returns 500 despite having saved part of the request. Treat a combined round edit as one atomic operation.

Course linking similarly fills destination hole and tee data in separate transactions before linking the round. A later failure can leave destination changes committed. Review transaction boundaries for the whole operation, including the returned round.

### Linking, tee authority, and historical data

- This router copies `round_.user_tee` first, whereas `Round.get_tee()` prefers a matching course tee. Apply one authoritative tee-selection policy.
- The route describes linking an unlinked round but also permits changing an existing linked course; the frontend uses this for course changes. Make that supported behavior explicit. When the destination lacks a hole, the repository does not clear that score's previous `hole_id`, so a relink can leave a hole reference to the old course. It also retains existing `par_played`/`handicap_played` via `COALESCE`; define historical-data behavior when correcting a course association.
- Access checks cover round ownership, list user identity, and private destination-course ownership. Filling destination metadata is restricted to the current user's custom courses. No access-control bypass was identified in this review; add regression coverage for rejected cross-user operations.
- The route fetches the destination course again after `_check_course_access` already returns it. Reuse that result, and consider moving linking orchestration into a service during the architecture review.

## `api/routers/scan.py`

Review started October 3, 2026. Implementation remains deferred.

User confirmed that the presence-based confidence behavior needs fixing and that extraction responsibilities should move out of the router where appropriate. Treat confidence meaning as a priority correctness fix, with responsibility separation as a related refactor. Preserve this distinction when planning implementation.

### Confidence thresholds and meaning

**User requested direction:** raise score-confidence categories to high at 0.90 and medium at 0.70, from the current 0.85 and 0.65. Record these as classification thresholds, not a guarantee of scan accuracy. The current helper also categorizes putts, GIR, hole-level confidence, and scan-level confidence; decide their scope during implementation.

**Confirmed issue:** `_build_confidence_payload` assigns fixed numeric values based solely on presence: strokes 0.90/0.20, putts 0.85/0.25, and GIR 0.80/0.30. The builder receives assembled values and warning strings, not per-cell recognition confidence. Every non-null stroke is therefore high confidence, including one read incorrectly or inferred/corrected by a heuristic. Changing category thresholds alone cannot distinguish reliable and questionable non-null strokes.

Scan-level confidence is the fraction of non-null stroke values, reduced by warning count. Hole-level confidence is the minimum of stroke and putt presence scores, ignoring GIR. A scan with all strokes present and no putts can consequently report overall 1.0/high while every hole reports 0.25/very_low. Missing optional statistics should not reduce confidence in readable strokes; presence/completeness and recognition confidence need separate meanings. `validation_flags` is always empty even when assembly produces validation warnings.

Deferred direction: preserve evidence about extraction, ambiguity, validation, corrections, and whether a value was observed or derived. Use available evidence for review decisions and avoid presenting unsupported numeric estimates as measured accuracy. Validate any future probability interpretation against labeled examples. The existing extraction path does not pass per-field confidence into this builder.

### Assembly logic: hole identity and partial data

- Unknown courses default to 18 holes. Known courses instead derive `hole_count` from the number of stored hole objects and construct numbers 1 through that count. This ignores intended format and sparse/back-nine hole identities. Reproduced: two stored course holes truncate 18 scanned scores to two; course holes 10–18 produce output holes 1–9 and discard aligned back-nine scores. Align data by explicit hole number and intended hole set.
- Known-course metadata does not fall back to parsed par when a stored hole/par is missing. Coordinate this with the shared par-authority policy.
- Unknown-course par becomes the sum of known pars as soon as nine are present, even while the output still contains 18 holes. Reproduced: nine known par-4 values and 18 scores produce course par 36 without a warning. Distinguish a complete nine-hole par from partial metadata for an 18-hole round.

### Score validation and derived GIR

- GIR is derived from the raw shots-to-green value before that value is range-validated. Reproduced: shots to green of zero become null but still produce GIR true.
- Shots to green can exceed known total strokes; this is the same cross-field gap identified in requests and domain models.
- Invalid non-null raw scores and invalid converted scores become null without an explicit warning; invalid shots to green also become null silently. Reproduced: a score of 16 yields null strokes with no review warning. Keep invalid/missing/unplayed states distinct and report validation outcomes consistently.
- Birdie/bogey sign correction assumes shots plus putts reconstruct total strokes. It has a `sign_evidence_trusted` guard, but still depends on the unresolved definition of shots to green and penalties. Preserve raw evidence and correction status, and include corrections in review decisions.
- Sign correction separately caps putt evidence at six, while the agreed putt range is 0–10. Determine whether this is an intentional evidence rule or a duplicated limit; do not widen it without reviewing the sign-disambiguation behavior.

### Review contract with the frontend

Warnings are free-form strings. The review banner filters for the word `strokes`, so warnings such as `Hole 1 score sign corrected` or `cannot convert to-par score without known par` do not affect that banner. Review-item construction also relies on per-stroke confidence labels, but all non-null strokes receive high confidence. Use structured issues with hole number, field, reason, and severity so review behavior does not depend on prose matching. Coordinate the API contract with the frontend during implementation.

### Structure and naming

`_build_round_from_parsed_rows` mixes course projection, hole alignment, row padding, scoring-format selection, sign correction, validation, GIR derivation, and response assembly. Its numerous parallel lists and positional indexing make ordering and identity bugs difficult to inspect. Repeated padding loops and broad `getattr` access are also candidates for simplification using typed data.

Refactor toward explicit stages: resolve course/hole metadata; align parsed values by hole; interpret scores; validate and derive fields; collect review evidence; serialize the result. Keep orchestration in a scan extraction service and HTTP validation/error handling in the router. Use names that expose meaning, such as `hole_number`, `raw_score_value`, `score_to_par_delta`, `resolved_strokes`, and `validated_shots_to_green`; give the course argument its actual type. The code after assembly also contains upload storage, image preprocessing, provider orchestration, timing/logging, and cleanup in the router. Group those responsibilities behind focused components where it improves clarity, without splitting every small operation into its own abstraction. The save route already delegates to `ScanService`.

Verification: local calls to the real assembly/confidence helpers reproduced the confidence contradiction, invalid GIR derivation, shots exceeding strokes, silent invalid-score removal, score truncation, back-nine misalignment, and partial par treated as a course total. No external provider or database was called.

### Temporary-file ownership and cleanup

- `_save_upload_to_temp` uses `delete=False` and deletes on the oversized-upload path only. A read/write failure after creating the file leaves it behind; the caller has not received its path and cannot clean it up. A local injected read failure reproduced the leak.
- `_normalize_upload_for_ocr` can create a generated file and then fail while encoding/replacing it. Its broad fallback returns the original upload without removing the newly created artifact. An injected JPEG-save failure reproduced an orphan output file.
- Extraction cleanup calls `unlink` without handling filesystem errors. A cleanup error can replace the original structured scan error or turn successful extraction into a failed response, and can skip cleanup of the other file. Reproduced: a simulated cleanup `PermissionError` replaces an intentional 422 `ScanExtractionError`. Prefetch cleanup already suppresses `OSError`; establish shared cleanup ownership and preserve the primary outcome, logging cleanup failures for diagnosis.

### Blocking work inside asynchronous endpoints

Both `/ocr` and `/extract` directly run synchronous upload reads/writes, Pillow verification, decoding, resizing, and JPEG encoding before awaiting provider work. These operations occupy the event-loop thread and can delay other requests. Move appropriate file/image work to a worker thread or use async upload I/O, keeping resource cleanup correct when work fails or is cancelled. This is a code-path finding, not a measured production performance result.

### PDF validation and page handling

PDF validation checks only the first five bytes for `%PDF-`. A local file containing that prefix followed by arbitrary text passes. Validate that the PDF can be parsed before treating it as a supported document and map malformed documents to upload errors.

Normalization attempts to open a PDF with Pillow and keep only page one; if that fails, it sends the original PDF to OCR. Define a consistent supported page policy so fallback behavior does not change which scorecard pages are processed. Review this with the OCR service and multi-page examples.

### Error messages and diagnostics

- When no strokes are extracted but `parsed_rows.player_name` is present, the route says the name is unclear. A detected name does not establish that cause. Reproduced using a recognized name and empty score rows. Report missing/unreadable scores or the actual conversion/alignment failure rather than claiming name recognition failed.
- Input validation outside the extraction try block and the prefetch endpoint use plain HTTP exceptions, while later extraction failures use structured categories/stages. Align the contract used by the UI and failure reports. Zero valid strokes after assembly is hardcoded as a parse failure even when missing par or conversion caused it; preserve the actual cause and stage.
- Save validation failures all become a generic 400, and other exceptions become 500. Review service error types for missing/inaccessible courses, conflicts, and invalid score data so expected failures have useful, safe messages and statuses. The route correctly derives `user_id` from the authenticated user rather than trusting the submitted value.

### Unnecessary database dependency for anonymous OCR

`prefetch_ocr` has no database work but depends on `get_optional_current_user`, which unconditionally depends on `get_db`. A database outage therefore stops even anonymous OCR before its provider is invoked. Reproduced through an isolated FastAPI app without an initialized DB: `/ocr` returns 503 and never calls the fake OCR pipeline. Extraction without a selected course is also coupled through these dependencies and its explicit `db` dependency. Separate optional authentication/course lookup availability from processing that does not require database data; preserve access checks for private courses.

### Response typing and smaller cleanup items

- `ScanResponse` declares unrestricted `dict`/`list` fields; nested hole scores, course metadata, confidence records, and issues are not checked against a defined response contract. Add dedicated response types appropriate for partial extraction data when the revised review contract is established.
- Preprocessing caching is disabled. If enabled, the current helper does not read an existing cached artifact, always reports a miss, and callers remove the generated cache output. Either remove the unused mechanism or implement and test its actual lifecycle; it is not an active cache today.
- `MISTRAL_OCR_MODEL` is declared in the router but unused; the OCR service resolves its own model configuration. Keep provider configuration in one authoritative place.
- The maximum OCR-text length is checked for client-supplied prefetched text, while fresh provider output bypasses that check. Establish one text-size policy for both paths.

Additional verification used fake provider/parser boundaries, injected filesystem failures, temporary files cleaned after the reproductions, and an isolated FastAPI app. No live OCR provider or database was accessed. Keep regression cases for these failure paths with the eventual fixes. Detailed OCR-service behavior, PDF processing, save-service error semantics, and cross-user integration coverage remain follow-ups as their folders are reviewed.

## `api/routers/stats.py`

Reviewed October 3, 2026. Implementation remains deferred. The file delegates many calculations to analytics helpers and has clear endpoint boundaries, but it still mixes HTTP handling, data-window selection, KPI calculation, response defaults, and milestone presentation.

### Large empty response and response-contract drift

Lines 153–309 hand-build the complete empty analytics payload. This duplicates the populated contract and parts of `analytics.notable_achievements`, whose engine already accepts an empty round list.

Confirmed discrepancies: the empty API response omits `scoring_by_yardage`, while the populated response and frontend `AnalyticsData` require it. ### Eligibility for scoring, records, and missing observations

- Dashboard scores include every non-null SQL total; analytics scoring averages include every non-null `calculate_total_score()` result. Neither checks intended format/completeness. Reproduced: a one-hole round appears as scoring average 4 and achieves a break-60 milestone; mixing its score 4 with an 80 produces dashboard best score 4 and average 42. Define round-level eligibility while permitting appropriate hole-level analysis of known observations.
- Dashboard inherits SQL-summary handling that turns unknown GIR into zero and compares partial scores against full-course par. Reproduced: one up-and-down success on a one-opportunity round plus zero successes on a nine-opportunity round produces 50%; the percentage over all ten opportunities is 10%. Decide whether each KPI is an average of round percentages or an overall opportunity-based rate, label it accordingly, and share the policy.

### History limits and meanings of totals/lifetime/first
