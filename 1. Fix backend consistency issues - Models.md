## October 15, 2026 — approved model implementation

Implemented locally on `models-domain-refactor` for integration into `backend-refactor`, not direct production release:

- Atomic direct assignments, `update_field()` and coordinated `update_fields()` validate an isolated candidate before changing values, fields-set or freshness state. `Round.update_hole_score()` and `Tee`/`UserTee.update_yardages()` are the supported correction paths. Yardage mappings reject ordinary in-place mutation.
- Explicit `Course.total_holes` (9/18), `Round.intended_holes` (1–9 / 10–18 / 1–18), and `HoleScore.played` distinguish layout, round intention, skipped holes and unread scores. Nine entries alone do not establish a nine-hole course/complete round; canonical unique eighteen-hole coverage remains an unambiguous legacy inference.
- Identified scored holes drive partial strokes and same-set to-par. Duplicates are ambiguous, unnumbered scores remain review data rather than totals, and accepted `par_played` precedes current course par. Full aggregate par requires complete coverage; supplied whole-course summaries remain usable without child par observations but do not establish a layout.
- Child observations take priority over supplied putts/GIR/par/yardage totals. Putts/GIR require observations on every identified scored hole, preserving zero/False. Update tracking prevents stale totals resurfacing after child values are cleared. Serialization emits the resolved totals so a JSON reload cannot make a stale summary authoritative again.
- Shared tee rules enforce integer hole keys 1–18, reject normalized aliases, and accept integer yardages 0–1,000 inclusive. Unknown yardages are omitted, not null; no manual-yardage UI is planned. Explicit `yardage_holes` scopes totals; `rating_holes` and `TeeRating` records scope positive finite course ratings and slopes 55–155. `get_rating()` requires exactly matching coverage, never halves ratings or infers format from rating magnitude.
- Shots to green and putts cannot individually exceed known strokes. No sum-equality rule was added. Net strokes are gross minus applicable allocated handicap strokes, not to-par or raw Handicap Index; absent context remains unknown. Stored per-hole net accepts signed 32-bit integers, pending database constraint alignment.
- Shared exact labels include condor at -4, albatross at -3, and numeric labels outside the named range. Analytics chart group keys are unchanged.
- `User.scoring_goal` remains the eighteen-hole target (18–270); `scoring_goal_nine` is a separate optional nine-hole target (9–135). Front/back nine use the nine-hole format.
- `Course.has_required_course_data(selected_tee=None)` checks structural readiness: layout, complete hole pars, at least one uniquely named tee with complete yardages, and complete selected-tee yardages if selected. Ratings are optional. It does not verify identity, provenance, or persist anything. Tee selection remains optional and legacy course-first resolution is preserved.
- Regression coverage is in `tests/test_models.py`; the shared known-format fixture now explicitly declares intended/rated coverage. No application code outside `models/` was changed.

Validation: full backend unit suite (`pytest -q --ignore=tests/integration`) **682 passed**; focused Models/Analytics/Handicap/Database/Scan tests **206 passed**; `ruff check .` and `git diff --check` passed. No live provider calls, database integration tests, migrations, commits or pushes were performed. Unrelated `.DS_Store` changes and other local review documents were preserved.

### Integration checklist — required in later domain branches

- API/Database: carry and persist course layout, intended holes, played state, yardage/rating coverage and rating records, and nine-hole goals. Audit/backfill historical format only from reliable context; do not guess a complete nine from row count. Align yardage/rating/par/net/goal constraints and null normalization; preserve accepted historical par snapshots on course edits.
- Services/API/Database: resolve known courses/tees DB-first without routine provider credits; verify new-course identity and tee mapping, prefer matched provider yardages over conflicting scan values, and track verification/correction provenance. Existing stored courses are not automatically proven verified by this model change.
- Save orchestration/UI: run source verification and structural completeness before any course/round writes. Missing required course data or failed verification must save neither record, retain review/image data, and explain that nothing was saved with re-scan/retry options. Missing optional player stats are allowed. No guessed tee or manual yardage entry.
- Analytics: use matching published rating coverage, format-specific round/goal eligibility and raw averages, and hole-based denominators including nine-hole observations. The existing handicap engine was not rewritten and still needs the separate approved nine-hole policy integration.
- Callers must use validated replacements rather than mutating yardage dictionaries, and resolved getters/serialization rather than treating old raw summary fields as authoritative after nested edits. Ordinary score/holes lists remain review containers; the model correction methods provide validated edits.

## `models/base.py`

- Provides shared Pydantic assignment validation and the `update_field()` helper.
- Later review of `HoleScore` identified an update-safety issue: an `after` model validator can reject an assignment after the object has already changed. `update_field()` catches the error but does not restore the original state.
- Reproduced locally: starting with `strokes=5, putts=4`, `update_field("strokes", 3)` returns an error while leaving `strokes=3, putts=4` on the object.
- Deferred change: ensure rejected updates preserve the previous valid state. The user agreed this needs addressing.

## `models/course.py`

The class structure and shared-model inheritance appear suitable for the behavior reviewed. The identified changes concern calculation and validation logic; no structural refactor has been proposed.

### Nine-hole par calculation

`calculated_par` currently requires exactly 18 hole entries. A complete nine-hole course with all hole pars available returns `None` when its total par is not stored explicitly.

Deferred change: support complete nine-hole and eighteen-hole courses, with an explicit rule for the expected hole numbers. Preserve an unknown total when required par data is missing rather than presenting a partial sum as the full course par.

### Front-nine and back-nine completeness

The ranges are correct for standard numbering: holes 1–9 and 10–18, inclusive. A standalone nine-hole course numbered 1–9 has a front-nine par and no back-nine par.

The current checks return `None` when fewer than nine entries are available or any selected hole has a missing par. However, counting entries does not ensure each expected hole number appears exactly once. Duplicate entries could hide an absent hole or inflate the sum.

Deferred change: validate unique expected hole numbers and known pars before calculating each nine's total.

## `models/hole.py`

No change identified in this review. The simple field model is appropriate. Checks involving multiple holes, including complete numbering and unique handicap rankings, belong at the course level.

## `models/round.py`

The overall structure is appropriate: the model contains round data, looks up related holes and tees, and calculates domain results. It has no database queries or API responsibilities. No broad structural rewrite is proposed.

Focused structural improvements remain useful: share aggregation logic, centralize par resolution, and represent intended holes explicitly. Keep the public convenience methods where they express distinct operations. These directions are recorded for later planning; implementation is deferred.

### Tee selection

`get_tee()` first looks up the course tee matching `tee_box`, then falls back to `user_tee`. The course lookup already uses the player's selected tee label; it does not choose an arbitrary course tee.

The user questioned whether a selected custom tee should take precedence. If the linked `user_tee` represents the configuration explicitly selected for this round, it should be authoritative. Define how `tee_box` and `user_tee` relate when both exist, and how subsequent tee edits update those references. Reversing priority without establishing that contract could return a stale custom selection.

### Consistent totals and missing data

- `get_total_putts()` considers holes with recorded strokes and returns `None` if any of those holes lacks putts.
- `get_total_gir()` counts known GIR observations, including entries without recorded strokes, and ignores unknown observations. Two hits with seven unknown observations can return a total of two.
- Total, front-nine, and back-nine stroke methods sum available scores without requiring completeness.

Deferred change: define the relevant hole set and missing-data policy for each total. Distinguish an observed partial count from a complete total, and preserve known zero values separately from unknown values.

### Total score and the two nines

`calculate_total_score()` has a useful independent purpose: the API, persistence layer, and analytics consume the overall score. Front-nine and back-nine methods provide its breakdown.

The user suggested composing the overall total from the two nine totals. That is possible only after defining how an absent nine differs from an incomplete nine. A complete nine-hole round should have a total even when the other nine is absent.

Proposed direction: let all three methods use a shared summing helper with the appropriate hole range and completeness policy. Keep the overall total method available to callers.

### Round completeness

`is_complete()` guesses nine versus eighteen from the number of entries and counts non-null strokes. It does not establish the intended holes or validate unique hole numbers. Duplicate entries or scores with missing hole numbers can satisfy the current count.

Deferred change: define the intended hole set, including front-nine and back-nine rounds, and require exactly one known score for each expected hole. Distinguish a complete nine-hole round from an incomplete eighteen-hole round. Decide how intentionally unplayed holes differ from scores the scan failed to read.

### Par resolution and calculation methods

`get_hole_par()` uses `par_played` only when no course is linked. A linked course with a missing hole or missing par prevents fallback to an available historical `par_played`.

`get_par()` bypasses per-hole resolution: it returns linked course par, or sums available `par_played` values when no course exists. That fallback can present a partial par sum as the round's total par.

The methods have distinct purposes: resolve one hole's par, resolve aggregate par, calculate one hole relative to par, name its result, and calculate the aggregate result. `score_to_par()` and `get_score_type()` already delegate to `HoleScore`, which is appropriate.

Deferred change: centralize par precedence and fallback, including whether historical `par_played` should override current course data. Have related methods use the same relevant holes and completeness policy. Keep calculations requiring missing par unknown.

### Partial rounds relative to par

A player skipping a hole affects round completeness and scoring. The course's par remains unchanged.

`calculate_total_score()` sums available strokes, while `total_to_par()` subtracts the full linked course par. This can compare scores and pars from different sets of holes.

Example: a player records 80 strokes over 17 holes on a par-72 course and skips a par-4 hole. The current calculation returns +8. The score relative to par for those 17 scored holes is +12, because their par totals 68.

Deferred change: if partial score-to-par is supported, compare strokes with par for those same scored holes and label the result as partial. Review eligibility before using partial rounds in whole-round comparisons, goals, or handicap calculations. Retain usable data for individual holes.

### Stored summary totals

`total_putts` and `total_gir` accept unrestricted integers, including negatives. When provided, they override calculated totals. Editing individual hole scores does not clear or update those supplied totals, so they can become stale.

Deferred change: define appropriate bounds and reconcile supplied totals with hole-level observations. Establish how score edits invalidate or recalculate stored summaries.

### Scores without hole numbers

`calculate_total_score()` includes recorded strokes even if `hole_number` is missing, while front-nine and back-nine totals exclude those entries. An unnumbered score of five can therefore increase the overall total without appearing in either nine or being matched reliably to par.

Deferred change: preserve incomplete scan data during review, then define whether an unnumbered score may contribute to a saved round's totals.

The exact round representation, tee authority, summary rules, and analytics eligibility remain to be decided during implementation planning.

## `models/hole_score.py`

### Score consistency

The validator only checks putts against strokes. It accepts impossible combinations such as `strokes=4, shots_to_green=8`.

Deferred change: check shots to green against total strokes when both are known. Define whether shots to green includes penalties and all non-putting strokes before enforcing `shots_to_green + putts == strokes`. Keep missing values unknown.

### Field limits and API agreement

User decision: the existing limits should apply everywhere, including manual entry and scans: strokes 1–15, putts 0–10, and shots to green 1–10.

The domain model and database limit `net_score` to -3 through 15. Define its meaning before finalizing the bounds and apply them consistently. The API mismatch is recorded in the [API review notes](<1. Fix backend consistency issues - API.md>).

### Par selection

`to_par()` correctly calculates strokes minus par and returns unknown when required data is missing. A supplied par overrides `par_played`, and the supplied argument is not validated.

Deferred review: define par precedence for historical rounds and validate supplied par values. No final precedence decision has been made.

### Shared classification and labels

Deferred direction: use a shared backend scoring function and a module-level label constant. `HoleScore.get_score_type()` can delegate to it. Analytics can group exact results into chart categories separately; its current classifier uses different labels and buckets.

User direction: albatross should match exactly -3; lower values should not be mislabeled as albatross. The upper-end rule is interpreted as exact names through +4 (quadruple bogey), then exact numeric labels such as `5 over`, `6 over`, and so on, rather than a single `5+ over` bucket. These differences are relative to par, not absolute stroke counts.

The user suggested rejecting results below -3 because a hole-in-one on a par five seemed impossible. Such scores are rare but have been recorded; a par-five hole-in-one is four under par, called a condor ([Golf Monthly](https://www.golfmonthly.com/features/the-game/has-there-ever-been-a-hole-in-one-on-a-par-5)). The lower-end acceptance and naming policy remains unresolved; consider preserving the score with an exact numeric label such as `4 under` instead of rejecting it solely for rarity.

All changes in this section remain deferred.

## `models/tee.py`

### Per-hole yardage limit

User decision: allow per-hole yardage from 0 through 1,000 yards, inclusive, across all layers.

Apply the limit consistently across domain models, API inputs, database constraints, and relevant tests. Confirmed 700-yard checks exist in `models/tee.py` and `database/schema.sql`; corresponding API checks are recorded in the [API review notes](<1. Fix backend consistency issues - API.md>). Existing databases will require a constraint migration. `UserTee` currently has no equivalent model-level yardage validator; include it in the consistency review.

The current lower limit differs: `Tee` permits zero while API validation and the normalized yardage table require at least 50 yards. The agreed minimum is now zero. Unknown yardages remain distinct from an explicit zero.

### Stored versus calculated total yardage

`get_total_yardage()` already returns `self.total_yardage` when supplied. If it is unknown, it sums available per-hole yardages; an empty dictionary returns `None`. The calculated fallback is returned without storing it on the object.

The fallback has a completeness issue: even one known hole can produce a value presented as total yardage. Define whether the result is a partial observed sum or a complete total for the intended holes. Also review how supplied totals are reconciled with hole yardages and invalidated when yardages change.

### Nine-hole course ratings

`course_rating` is constrained to 55–85, preventing ratings below 50 from entering this model. The handicap calculation has a path for shorter rounds with ratings below 50, so these contracts conflict.

Deferred change: account explicitly for the rated hole format and align rating validation across models, API inputs, scan normalization, persistence, and handicap logic. The supported ranges and format representation remain to be decided.

### Direct dictionary edits bypass validation

Assignment validation does not intercept mutations inside `hole_yardages`. Reproduced locally: after constructing a valid tee, setting `tee.hole_yardages[1] = 1500` and `tee.hole_yardages[19] = -20` succeeds without validation. A supplied total also remains unchanged after those edits.

Deferred change: establish a validated yardage-update path that checks the complete proposed dictionary before accepting it, and reconcile stored totals after successful edits. Consider how to prevent callers from bypassing that path through direct mutation.

No broad structural change identified. All implementation remains deferred.

## `models/user_tee.py`

The simple field-model structure is appropriate; no broad structural refactor is proposed.

- **Nine-hole ratings:** `course_rating` has the same 55–85 restriction as `Tee`. Include `UserTee` in the rating-format and cross-layer consistency work described above.
- **Missing yardage validation:** the model accepts invalid hole numbers, negative yardages, and yardages above the agreed 1,000-yard cap. Reproduced locally: `{19: -20, 1: 1500}` passes construction. Share the agreed 0–1,000-yard range and hole-number rules with `Tee` and API validation.
- **Unknown yardages:** the API accepts `{1: None}`, but the model's `Dict[int, int]` rejects that input. Decide whether unknown values should be retained or entries omitted, then apply the same representation through requests, models, and persistence.
- **Dictionary mutation:** direct edits inside `hole_yardages` bypass assignment validation. Include this model in the validated-update approach proposed for `Tee`.

All implementation remains deferred. The yardage range is decided at 0–1,000 inclusive; unknown-yardage representation remains undecided.

## `models/user.py`

The field-model structure is appropriate and contains no calculation methods. No broad structural refactor is proposed.

`scoring_goal` accepts unrestricted integers in the domain model, including negative values. The database declares `SMALLINT` without a goal-range check. The differing update API bounds are recorded in the [API review notes](<1. Fix backend consistency issues - API.md>).

Deferred change: establish the authoritative scoring-goal range and enforce it consistently in the model, API, and database. Include existing-data handling when adding a database constraint. No new goal-range decision has been made in this review.
